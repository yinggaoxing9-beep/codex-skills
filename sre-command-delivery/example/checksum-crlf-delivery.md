# 校验清单 CRLF 造成 Linux 交付入口失败

## 来源与范围

2026-10-14 用户交付反馈与本地原始字节核验。已脱敏，不保留节点地址、任务目录、凭据或当前部署参数。案例只说明交付验收缺口，不授权后续环境变更。

## 已观察到的故障

在 Windows 用 Python `Path.write_text(..., encoding="ascii")` 生成 SHA256SUMS 时，没有指定换行策略；文件实际以 `\r\n` 结尾。Linux `sha256sum -c` 把行尾 CR 当成压缩包文件名的一部分，报告文件不存在。压缩包实际存在，因为命令以 `&&` 串联，校验失败时没有进入解压。

此前通过的验证覆盖部署入口、真实 Ansible 的离线 fixture、更新器备份和幂等行为，以及 Python 直接计算压缩包摘要；没有用最终生成的外部清单执行实际 Linux 交付命令。因此“程序正确、摘要正确”仍没有覆盖清单的编码与格式。

## 原因与规则生效审计

当时读取过的部署技能有通用的复盘与验收要求，但没有明确的 LF/BOM、原始字节和最终清单消费要求。这不是已经明确写了 CRLF 规则却未被读取的证据；直接失误是遗漏最终交付入口。通用验收规则也没有落实到全部交付文件。

核验时还发现：源仓库与本机 sre-command-delivery 不是同一版本；本机另有 harden-deployment-automation 的返工复盘段，而该技能不在指定的源仓库内。版本差异不直接导致 CRLF，但说明不能只凭源文件存在就断言本机已经采用。新增规则应同时核对源仓库、本机副本和实际读取位置，保留无关既有差异。

## 修复与实际结果

源校验文件改为直接写入 ASCII LF 字节；归档内容及其摘要未变。先在本机 Linux 临时目录复现 CRLF 清单，再用删除读取流中的 CR、标准 sha256sum 校验、解压的顺序验证恢复；另验证修正后的 LF 清单。

用户随后报告摘要校验 OK、检查模式 CHECK_OK、应用模式 UPDATE_OK。现场只有初始化入口需要替换，两个依赖文件已经一致；更新器打印了备份位置。这个结果证明交付入口和代码更新完成，不证明主机名准备、sudo 延迟或后续 os-init 已恢复。

## 防复发验收

生成时显式控制字节；写出后检查 CRLF/BOM；使用最终清单和最终命令在目标系统的隔离目录验收。覆盖清单格式异常、摘要不符停止解压、正确格式成功三种行为。不要仅添加复盘文字而遗漏可执行验证，也不要将所有物料归档问题一律归因换行。
